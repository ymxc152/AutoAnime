# 扫描方案历史记录保护设计

## 目标

当扫描方案已经产生扫描记录或整理计划时，保留方案及其历史数据，只允许停用或重新启用；只有从未被任何扫描记录或整理计划引用的方案才允许删除。

## 现状与原因

后端当前已经检查 `scan_runs` 和 `plans`，发现引用时返回业务错误；数据库中的相关外键也使用 `RESTRICT`，防止删除方案级联破坏历史。前端目前仍显示“删除”，因此用户点击后才看到错误。

## 设计

- 后端继续以 `scan_runs` 或 `plans` 任一计数大于零作为“有历史”的判定。
- 有历史的方案不改变数据库记录，不删除扫描结果、整理计划或操作追踪；API 通过已有的 `PATCH /api/v1/profiles/{id}` 更新 `enabled=false`。
- 无历史的方案继续使用现有删除 API，并保留乐观锁 `revision` 校验。
- 前端根据当前方案返回的 `enabled` 状态提供“停用/启用”操作；对于有历史的方案不显示删除按钮。列表接口一次性返回每个方案的 `scan_runs` 与 `plans` 计数，避免逐行请求；这两个字段仅用于操作权限展示，不改变方案实体更新接口。
- 手动扫描、Webhook 和定时任务继续依赖 `enabled` 状态，停用后自然不可再触发。
- 发生并发修改时继续显示现有修订冲突提示；停用失败不影响历史数据。

## 验证

- 服务测试：有扫描记录时删除仍被拒绝；有整理计划时删除仍被拒绝；无历史时删除成功；停用只更新 `enabled` 且保留记录。
- API/UI 测试：列表能区分有历史和无历史方案；有历史方案展示停用/启用而不展示删除；停用后手动扫描按钮不可用。
