# 扫描方案逻辑删除与历史快照设计

## 目标

允许删除已经产生扫描记录、整理计划或回滚审计的扫描方案，同时保证历史记录可读、可追溯且不破坏现有外键关系。

删除方案后：

- 方案不再出现在当前扫描方案列表中；
- 后台保留一份完整的删除快照；
- 扫描运行、整理计划和操作/回滚审计继续保留并显示历史方案信息；
- 运行记录不因方案删除而自动删除；
- 定时任务和 Webhook 等当前自动化配置随方案删除；
- 仍在排队或执行中的扫描任务阻止删除，避免任务引用失效配置。

## 现状与问题

`scan_runs.profile_id` 和 `plans.profile_id` 使用 `ON DELETE RESTRICT`，`ProfileService.delete_profile` 也会主动拒绝存在历史记录的方案。该保护避免历史数据损坏，但导致目录删除提示用户先删除方案，而有历史的方案又无法删除，形成操作死路。

历史数据还只保存 `profile_revision`，没有保存该版本的方案配置。即使解除外键限制，历史页面也无法可靠还原当时的方案名称、目录、模式和执行策略。

## 设计决策

### 1. 方案采用逻辑删除

在 `scan_profiles` 增加：

- `deleted_at`：逻辑删除时间，可为空；
- `deleted_snapshot_json`：删除时保存的完整方案快照，可为空。

删除接口保留现有修订号校验，但不再执行物理 `DELETE`。事务内完成以下操作：

1. 检查方案存在、修订号匹配；
2. 检查该方案是否有状态为 `queued`、`running` 或 `leased` 的扫描任务；有则返回业务错误；
3. 读取方案及其绑定源目录、媒体库目录和规则配置，生成快照；
4. 写入 `deleted_snapshot_json`、`deleted_at`，并将 `enabled` 与 `watch_enabled` 设为关闭；
5. 删除该方案绑定的 schedules 与 webhook_sources，因为它们是当前自动化配置，不是历史运行记录；
6. 提交事务。

方案列表、自动化配置列表和所有创建/更新方案的入口只处理 `deleted_at IS NULL` 的方案。已删除方案保留数据库行，以兼容现有历史外键和查询链路，但不可再次编辑、启用或发起新扫描。

### 2. 历史记录保存扫描时的方案快照

在 `scan_runs` 和 `plans` 增加 `profile_snapshot_json`，内容至少包括：

- 原方案 ID、名称和修订号；
- 源目录 ID、路径及媒体库 ID、路径；
- 文件模式；
- 执行策略；
- 最低置信度和稳定等待秒数；
- 目录监听与启用状态；
- 关联规则配置及规则版本；
- 快照生成时间。

扫描开始时从同一事务中的当前方案和根目录生成快照并写入 `scan_runs`。创建计划时复制扫描运行快照到 `plans`，后续同一扫描运行产生的计划修订继续使用同一快照。操作批次和回滚审计通过 `operation_batch -> plan -> profile_snapshot_json` 读取历史方案信息，不新增重复字段。

### 3. 已有数据库的迁移

Schema 版本递增。迁移必须幂等：

- 给 `scan_profiles`、`scan_runs`、`plans` 添加缺失列；
- 对已有方案生成可序列化的当前配置快照；
- 对已有扫描运行按 `profile_id` 回填 `profile_snapshot_json`；
- 对已有计划优先复制对应扫描运行快照，缺失时按 `profile_id` 回填；
- 不改写既有运行、计划和操作记录的状态，不删除任何历史数据；
- 重复运行迁移不得重复覆盖已存在的快照或重复执行删除逻辑。

### 4. 删除后的运行与计划行为

运行记录、待确认项、整理计划和已完成/失败的操作批次继续可读。已创建的计划仍可依据自身快照完成原本的审批与执行流程；删除方案只阻止新的扫描配置入口，不撤销已经创建的工作。删除方案不会改变计划的 `profile_revision`，避免仅因配置隐藏而使已创建计划无故过期。

新的手动扫描、Webhook、定时扫描和目录监听不能使用已删除方案。已存在的扫描任务必须在方案删除前完成或取消；删除成功后不再允许新的扫描任务指向该方案。

### 5. 运行记录清理策略

本次不增加运行记录删除接口，也不在删除方案时级联清理运行记录。未来如需清理运行历史，应提供独立、显式且带影响范围确认的操作，明确其会删除扫描项、待确认项和无操作历史的计划，但不会逆向删除已发生的文件操作或回滚审计。

## API 与界面

- `DELETE /api/v1/profiles/{id}`：对有历史的方案也返回成功，响应保持 `{id, deleted: true}` 语义；重复删除返回方案不存在或已删除的业务错误。
- `GET /api/v1/profiles`：过滤逻辑删除方案；当前方案列表不显示已删除方案。
- 历史查询接口：返回解析后的方案快照或可直接展示的 `profile_name`、目录和模式字段，不要求当前方案仍是活动配置。
- 删除按钮文案明确说明会隐藏方案但保留历史记录；删除失败时展示“存在正在运行的扫描任务，请先等待或取消”。
- 删除方案后，目录仍可能因文件记录或整理计划引用而不能物理删除；此时目录继续使用停用操作。

## 错误处理与并发

- 删除继续使用现有乐观锁 `revision`；并发编辑时返回修订冲突。
- 删除事务使用同一数据库连接完成快照、标记方案和清理自动化配置，保证不会出现“方案已隐藏但快照未写入”的中间状态。
- 删除与排队任务创建之间必须在事务边界上检查；任务状态为 `queued`、`running` 或 `leased` 时拒绝删除。
- 已删除方案的更新、重新启用和新扫描请求返回明确的业务错误，不泄露内部 SQL 异常。

## 测试计划

### 数据库与迁移

- 新数据库包含新增字段；重复运行迁移保持成功且数据不变。
- 旧数据库能生成方案、扫描运行和计划快照；既有历史行数量与状态不变。

### 服务与 API

- 无历史方案可以逻辑删除并从列表消失。
- 有扫描记录、有计划记录的方案都可以逻辑删除。
- 删除后快照完整，运行记录、计划、待确认项和操作/回滚记录仍可读取。
- 定时任务和 Webhook 被清理，已删除方案不能创建新任务。
- 有活动扫描任务时删除被拒绝；修订号过期时仍返回冲突。
- 删除后已创建计划可按快照继续完成原有流程。

### WebUI

- 有历史方案显示删除入口，删除成功后从列表消失。
- 删除确认框说明历史记录会保留。
- 删除后刷新页面仍不显示该方案，历史页面仍显示正确的方案名称、目录和模式。
- 活动任务导致删除失败时显示中文业务提示。

## 非目标

- 本次不物理删除 `scan_profiles` 行。
- 本次不自动删除运行记录、整理计划、操作日志或回滚审计。
- 本次不提供运行历史清理功能。
- 本次不改变目录物理删除的历史数据保护规则。
