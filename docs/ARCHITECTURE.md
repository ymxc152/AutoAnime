## 运行形态(Architecture 决议 #1)

**单用户本地工具,明确不做多用户 Web 服务。**

- 部署形态:NAS/Docker 自部署,WebUI 只是本机/局域网控制台
- 由此推导:SQLite(单写者足够)、SSE 不按用户分流、API 仅需简单 token 防局域网误访问、docker-compose 一键起即完整产品
- 对标竞品(AutoBangumi/ani-rss/MoviePilot)均为同一形态;不引入认证体系/配额/数据隔离

**所有状态进 SQLite,废除文件态缓存。**

- 旧 AutoAnime 的 cache 文件体系(persistent/canonical/whitelist/trust 各自落盘)是长期不稳定的来源之一,全部不再移植

## 1. 领域模型(对标 Sonarr)

```
Series(番剧) 1 ── n Season(季) 1 ── n Episode(集) 1 ── n ReleaseRecord(种子候选记录)
```

- Series: title_cn / title_jp / title_romaji / tmdb_id / bangumi_tv_id / fansub_pref / quality_pref / status
- Episode 状态机:
  `MISSING(缺) → DOWNLOADING → DOWNLOADED(未整理) → ORGANIZED(已归档, 记 quality_score) → UPGRADED(被洗版替换)`
  分支:`IGNORED(手动放弃)`
- Season 状态机(季度记忆的核心):
  `UPCOMING → AIRING(每周放送,高频轮询) → ENDED(放送完毕) → COLLECTED(集齐)`
  - AIRING:每周 RSS 轮询 + **缺集检测**
  - COLLECTED 后降频为每月检查(只为了洗版机会)

## 2. 季度更新记忆(需求:番剧按季度放送,每周一集)

- 订阅时写入 Series + 预生成当季 Episode 行(MISSING),集数来自 bangumi.tv API / TMDB
- 每周轮询该番剧的 RSS:
  1. 新种子 → 三级识别 → (season, episode) 命中已有 MISSING 行 → 择优下载
  2. **缺集检测**:轮询后 diff [放送进度期望集数] vs [非 MISSING 集],缺口列表触发回补搜索
  3. 集齐(或放送结束且无缺口)→ Season → COLLECTED,轮询降频
- 记忆点:**"本季追更中"是 Series 级状态,重启/换机后从 SQLite 恢复,不依赖运行时内存**

## 3. 洗版引擎(需求:同集更高质量自动重下)

**质量评分公式**(release 候选与已归档文件通用):

```
score = 4 × 分辨率分(1080p=4, 720p=2, ≤576=1)
      + 3 × 来源分(B-Global/Baha/ATX WEB-DL=3, Web Rip=2, HDTV=1)
      + 2 × 编码分(HEVC=2, AVC=1)
      + 2 × 字幕组偏好(用户指定=2, 默认=1)      ← Series.fansub_pref
      + min(2, log10(seeders+1))               # 做种健康度,封顶防单点
```

**洗版规则**:
- 触发条件:`新候选 score ≥ 当前 score + 2`(阈值可配,防无意义反复下载)
- 单集洗版上限:默认 2 次(`episode.upgraded_count` 记录)
- 流程:新种下载到临时目录 → 校验完整性 → 原子替换(新文件改名入库 + 旧文件删除)→ state: ORGANIZED→UPGRADED→ORGANIZED
- 失败回滚:新文件校验失败则保留旧文件,release 记录 decision="rejected"

## 4. 多候选择优(需求:同集多种质量种子自动匹配最优)

- 同一 (season, episode) 出现多个候选时,统一走评分公式排序
- 择优只在两种时机发生:
  1. Episode = MISSING → 直接下最高分
  2. Episode = ORGANIZED → 只有触发洗版阈值才下
- 剔除规则:size 偏离同候选中位数 ±50% 以上视为坏包;seeders=0 且 age>7 天降权

## 5. 三级识别管线 + 记忆飞轮(差异化核心)

```
L1 anitopy: 纯本地,置信度=字段完整度(剧名+季+集齐全且无冲突)
L2 规则记忆: alias 表(番剧别名) + parse_memory(历史解析结论) 修正/补全
L3 LLM 兜底: 仅低置信度或 L1/L2 失败时调用
```

**记忆飞轮(越用越省的关键)**:
- L3 解析成功 → 结论写入 parse_memory(原始文件名模式 → 规范元数据)与 alias(别名→series_id)
- 下次同字幕组/同命名模式 → L1/L2 直接命中,LLM 调用率随使用时间单调下降
- **可量化指标**:"运营 N 周后 LLM 调用率从 X% 降至 Y%"(比一次性对比更硬的数字)

### 5.0a 扫描层:识别单元与上下文合并(2026-09-05 专题结论 A)

- **识别最小单元 = 视频文件**,不是文件夹。文件夹名(如 ...S01...-MWeb 整季包目录)只描述发布形态,内部文件(S01E06)才是集级事实
- 扫描两层:目录树按扩展名捞视频文件 → 逐文件识别;文件夹名作上下文佐证
- 字段合并规则:文件名与文件夹一致→直接用;文件名缺信息(如 6.mkv 极简方言 G)→文件夹补剧名/季;**冲突→文件名优先且整体降档**,不擅自选边
- 每条解析结果带 vidence 字段:记录各字段来自文件名还是文件夹,归错档可排查
- 测试 fixture 用 结构化 dir→files 样本,非扁平名字列表

### 5.0b 置信度档位边界(基于 Z:\下载 2608 真实样本,2026-09-05)

离散三档(决议见对话),语料快照在 notes/samples/,六类方言分析见 notes/samples/命名方言分析.md。

**HIGH(直接归档,零 API/LLM 成本)**
- 剧名+季+集齐备,且集数通过真实性校验,且无冲突
- 合法形态 1——整季包: 季号显式 + 无集数 → segment=SEASON_PACK(一等公民,不是缺集数异常)
- 合法形态 2——季号藏在标题内: 第二季/2！！/4th Season/篇名(如 Sennen Kessen-hen)由季数正则组抽取,集数合法即 HIGH
- 合法形态 3——双集数 14(86): 括号绝对集数与放送进度互验一致即 HIGH
- 合法形态 4——剧场版: 识别为 segment=MOVIE,不硬套集数

**MEDIUM(进 L2,记忆/别名能救则升级)**
- 季号缺失且上下文无法推断(纯方括号流 [64bitsub]...[08]、EP03 格式)
- 词内点导致标题重建存疑(BanG.Dream/FateGrand): 字段自洽但归属未定
- 中文-only 剧名,alias 表无命中

**LOW(进 L3 LLM 兜底;L3 再失败进待确认)**
- 字段冲突(矛盾集数、集数>已放送进度)
- 剩余噪声超过阈值、解析失败

**路由**: HIGH→归档;MEDIUM→L2 重评(升级或待确认);LOW→L3。档位只做路由,明细(missing_fields 等)随 ParseResult 返回供 UI/报表用。

### 5.0c L1 锚点切分与方言规则(2026-09-05 专题结论 B)

- **锚点切分法**:S01/1080p/WEB-DL/-发布组 是结构分水岭;S01 之前=剧名候选段,之后=技术段;**剧名段整段送验证,段内不切**(防 NANOHA.EXCEEDS.Gun.Blaze 类标题被切碎后各查到错误结果)
- MWeb 方言:Anime. 前缀剥离;friDay/DSNP/LINETV/Baha/CR/AMZN 进来源站表;词内点(BanG.Dream/FateGrand)靠标题重建+归属核验兜底
- 无集数 ≠ 异常:整季包/剧场版为合法 segment(见 5.0b)
- 方言全表见 notes/samples/命名方言分析.md(A-F + 极简文件名 G)

### 5.1 识别出错防线 —— 记忆写入门槛(防污染)

原则:**未经确认的解析结论不直接成为长期记忆**。

| 来源 | 沉淀路径 | 权重 |
|---|---|---|
| 用户人工纠正/确认 | 立即写入,source=manual | 10(最高,只能被新的人工纠正覆盖) |
| L3 结果 + 用户确认(dry-run 确认/待确认列表通过) | 写入,source=llm_confirmed | 3 |
| L3 结果自动归档(无 UI 交互) | 先进 pending 区,ORGANIZED 后 7 天无申诉自动转正 | 1 |
| L1/L2 命中已有记忆 | 只更新 hit_count,不改结论 | - |

额外校验闸门(写入前):
1. **元数据核对**:解析出的 (title, season, episode) 必须能在 Bangumi/TMDB 找到对应条目,否则进待确认队列
2. **冲突拦截**:解析结果与已有 episode 状态矛盾(如 E07 已存在,新文件又解析成 E07 但哈希不同)→ 拦截进人工队列,不自动归档

**自动确认通道(2026-09-05 专题结论 F,修订观察期规则)**

满足全部三条 → 免人工确认、免 7 天观察期,直接归档:
1. 剧名在 Bangumi/TMDB **精确命中**且类型过滤通过(见 5.6 类型过滤)
2. 集数过真实性闸门(不超放送进度、与已有集不冲突)
3. 上下文自洽(该剧在订阅中 / 同字幕组模板此前已确认)

- 自动定案照进审计日志;某类场景频繁被'撤销整理'纠正 → 自动收紧该类门槛
- 自主权限三档(保守/平衡/激进)用户可调,默认平衡:证据充分的 MEDIUM/LOW 自动定案,存疑才进人工
- 原则:**跳过人工是赢得的特权,不是默认权利**

### 5.1b L2 pattern 归一化设计(数据验证版,2026-09-05)

**两级 pattern key**(经 2606 真实样本原型实测):

- 一级 key = hash(fansub_norm + title_shape):458 个 key 覆盖 2606 文件,共享 key 覆盖 94.3% —— 承担主要命中
- 二级 key = hash(title_shape):额外覆盖仅 1.8%,保留为廉价 fallback,不作为卖点
- 归一化五步: token 分类 → 技术/来源/噪声丢弃 → 数字占位符化({ep}/{season}) → 标点统一+大小写折叠(词序不重排) → key 生成
- fansub 缺失(如 -MWeb 发布组)允许为空,只走二级且信任分要求更高

**实测数据快照**(原型脚本 scripts/pattern_probe.py,粗正则,数量级可信):

- 2606 样本 → 458 剧目级 key,平均 5.7 文件/key;TOP key 单键 23 集
- 309 个共享 key 覆盖 94.3% 文件 —— 人工确认 ~309 次即可覆盖当前真实库(飞轮上限的直接证据)
- 形态级跨字幕组合并 +47 文件,当前语料零同形异剧碰撞

### 5.2 人工纠正 = 一等学习事件(自动复用)

WebUI 待确认列表里用户改一个字段,系统自动完成三件事:
1. 写/更新 parse_memory:`raw_title_pattern → 纠正后元数据,source=manual`(pattern 做归一化:保留字幕组名+标题形态,去掉噪声,保证泛化复用而不是精确匹配单文件名)
2. 更新 alias(纠正出的别名 → series_id)
3. 若该 pattern 已存在错误旧记录 → 旧记录标记 deprecated,新 manual 记录顶替

效果:**改一次 = 教会一次**,同类命名后续全部自动走对。manual 记录永不自动覆盖。

### 5.3 负记忆(错误模式规避)

- L1/L2 曾给出错误答案且被人工纠正的 pattern → 记入 bypass_list
- 命中 bypass_list 的标题**跳过 L1/L2,直接进 L3**(不再重复犯同样的错)
- parse_memory 记录 correct_count / corrected_count,规则质量分 = 前者/后者,低于阈值自动降级回 pending

### 5.4 错误入库的回滚

- 所有文件操作走审计日志(已有机制),每条归档记录可逆(reverse instruction:移动/改名/删除的反操作)
- 用户在 UI 发现归档错误 → 一键"撤销此整理"执行回滚 + 触发 5.2 的纠正学习流程
- 被纠正前的错误文件在 UI 中标红提示"来自误识别,已回滚"

### 5.5 记忆质量监控(UI 报表)

- 待确认队列长度趋势(突增 = 出现新命名模式或规则失效,提醒维护)
- 各来源命中率:manual/llm_confirmed/llm_auto 各自的复用正确率
- LLM 调用率周曲线(飞轮效果可视化,@xyflow/react 管线页直接展示各级命中率)

**北极星指标:人工介入率**(2026-09-05 专题结论 G)

- 面板展示'本周 X% 文件零人工完成',目标 <2%
- 突增 = 出现新命名方言或仲裁失效,自动告警

### 5.6 元数据匹配层(第三方 API 归属中文名)

定位:介于识别管线与归档命名之间的独立层。L1/L2/L3 解出 (raw_title, season, episode) 后,
由本层把 raw_title 归属到正确的中文名番剧,产出规范命名与元数据。

**双 API 分工**:
- Bangumi API(bgm.tv,动画主力):name/name_cn 中日双名、别名、每季集数、放送日期;
  POST /v0/search/subjects 模糊搜索,GET /v0/subjects/{id} 详情,episodes 接口核对集数
- TMDB API(国际标准/交叉验证):search/tv?language=zh-CN,tv/{id}/season/{n} 集数与放送日,
  alternative_titles 拿别名;当 Bangumi 置信度不足时兜底

**两种模式(成本差异巨大)**:
1. 订阅模式(主流):Mikan 的番剧 RSS 本身携带 bangumi subject_id → 直接 GET 详情,
   0 次模糊搜索,一次拉取后全部缓存进 series/alias 表
2. 散装整理模式(历史遗留目录):走完整模糊匹配流程

**模糊匹配打分**(散装模式):
1. 归一化:NFKC 全半角、去字幕组/括号噪声、lowercase
2. 候选生成:Bangumi 搜索 raw_title 与清洗后标题各一次
3. 候选打分:rapidfuzz token_sort_ratio(name 与 name_cn 各算,取高)× 0.6
   + 年份接近度(文件 mtime vs 放送年)× 0.2 + 流行度(收藏数/rank)× 0.2
4. 阈值:≥0.85 自动归属;0.6~0.85 进待确认队列;<0.65 才触发 TMDB 兜底
5. 交叉验证:TMDB 与 Bangumi 用 标题相似度+放送年份 双条件互认,互认后两边 id 都存
   (tmdb_id + bangumi_tv_id 同时写入 series,后续任一来源都能命中)

**集数真实性校验**(拦截误识别的硬闸门):
- 解析出的 episode 号 > 该季已放送集数 → 判定误识别,进待确认(防 L3 幻觉)
- 放送日 > 今天 → 同上

**放送进度的来源与校准(2026-09-05 专题结论 C)**

- 订阅成功时从 Bangumi/TMDB 预生成全季集表(含每集 air_date)存 SQLite
- 已播集数 = 该季中 air_date ≤ 今天的集数个数;AIRING 每周轮询时自动校准缓存
- API 无集表时(新番刚开):**不硬拦截,降级为'未验证'进待确认** —— 宁可慢,不误杀

**类型过滤与反串台(2026-09-05 专题结论 D,补强上述打分规则)**:

- **类型硬过滤**:Bangumi 只保留'动画'类型候选(真人剧/游戏/书籍出局);TMDB 用 media_type 过滤 —— 防止剧名撞车匹配到真人电视剧
- 多候选时:**第一名得分 <0.85 且与第二名差距不大 → 不自动选**,但不再默认甩人工,交给仲裁器证据裁决(见 5.7)
- 交叉互认(Bangumi+TMDB 标题+年份双印证)才双写 id;两边打架 → 进仲裁

**缓存与限流**:
- 所有 API 响应缓存进 SQLite(subject/tv id → 元数据);已完结番剧元数据不变,缓存永久有效
- Bangumi 需自定义 User-Agent(带联系方式),限流约 1~3 req/s,退避重试;TMDB 免费 key 足够
- 频繁调用只发生在散装模式首次接入;订阅模式几乎零调用

**与记忆飞轮的衔接**:匹配成功的别名(name/name_cn/日文名/罗马音)全部写入 alias 表 →
后续同类命名 L2 直接命中;匹配失败进待确认,人工纠正后同样沉淀(见 5.2)
### 5.7 自动仲裁管线:Agent 作为验证器(2026-09-05 专题结论 E)

定位:替代'多候选不定案→甩人工'与'L3 失败→进待确认'的默认路径,人工队列降级为最后防线。

- Agent = **带固定工具清单的验证器**:查条目详情 / 核对集数与放送日 / 查 alias 表 / 查同字幕组历史 —— 工具主要是免费结构化 API + 确定性代码,token 成本趋近零
- 最多两轮,每轮动作清单固定,无自主规划 —— 守住 9.1 确定性纪律(AI 只做认知归属,不做决策)
- 裁决产物:结论 + 完整证据链(每条证据为什么指向它)写入审计日志
- 证据裁不动(候选证据矛盾/全部低分)才进人工队列
- 自治权只覆盖'识别归属'这类纯认知问题;花钱/不可逆动作(下载、删除)仍走确定性代码
- 实现位置:pipeline/arbiter.py,接口化插件(见模块化原则),关掉即回到保守模式

## 9. AI/LLM 介入边界与框架选型

### 9.1 框架选型:SDK 直调为主,LangGraph 只留一个节点链

判断依据:本项目的 LLM 任务是"文件名/失败上下文 → 结构化元数据 JSON"的单次转换,
没有多轮工具调用、没有自主规划——**不需要重型 Agent 框架**。

- 主路径:OpenAI 兼容 SDK + JSON Schema 结构化输出 + Pydantic 校验(复用现有多模型槽位轮换/容错)
- LangGraph:仅保留"解析 → 本地校验 → 带错误反馈重试(最多1次) → 放弃进待确认"这一个状态链,
  对应 AnimeAgent 已有代码,迁移成本低;简历保留 LangGraph 关键词,但架构上诚实地"薄"
- 明确不引入:自主 Agent 循环、工具调用链、多 Agent 角色扮演——它们对这个任务只增加 token 和不确定性

### 9.2 LLM 介入点(全项目只有 4 处)

| # | 介入点 | 输入 → 输出 | 频率 |
|---|---|---|---|
| 1 | L3 文件名解析兜底 | 原始文件名 + top-k 别名上下文 → {title, season, episode, fansub} | 仅 L1/L2 失败,随飞轮递减 |
| 2 | 别名语义归一 | 散装标题 vs 候选名列表 → 归属判断(可用 embedding 相似度替代) | 仅散装模式低置信度 |
| 3 | 纠正模式泛化 | 人工纠正样本 → 归一化 pattern 规则(也可纯代码实现,LLM 只做难例) | 随纠正次数 |
| 4 | 周报/通知摘要(可选) | 状态数据 → 一句话摘要 | 每周 1 次 |

**确定性边界(不使用 AI)**:下载决策、质量评分、洗版触发、调度轮询、缺集检测——全部是确定性代码。
"AI 只做非结构化转换,决策全部可解释可复现"本身是工程亮点。

### 9.3 省 Token 手段(按效果排序)

1. 三级管线 + 记忆飞轮:结构性节省,调用率随时间趋近于零(最大头)
2. 解析缓存:归一化文件名 hash → 结果缓存,同模式重复文件 0 调用
3. 机会主义合批:仅当待处理队列自然堆积 ≥5 个同目录同字幕组文件才打包(上限 20,逐项校验失败不连坐);订阅场景单文件快路径永不凑批(详见 9.3b)
4. 小模型路由:L3 先走便宜模型(gpt-4o-mini / gemini-flash / deepseek),低置信度才升级大模型(级联)
   (2026-09-06 拍板:v1 单模型可配,级联进 backlog——飞轮是省钱主引擎)
5. Prompt 瘦身:只发文件名 + top-5 别名 + 集数约束;system prompt 固定(命中 OpenAI/Anthropic 的 prompt caching)
6. 输出约束:max_tokens 限制 + JSON Schema,禁止闲聊;输出后先过本地校验(集数真实性/TMDB 核对),
   失败才带错误反馈重试一次,不无限循环

### 9.3b L3 调用契约:单文件快路径 + 机会主义合批(2026-09-05 专题结论 G)

- **单文件快路径是一等公民**:订阅场景每周 1-2 集,来一个处理一个,秒级归档,永不等待凑批
- 机会主义合批:仅当待处理队列自然堆积 ≥5 个'同目录+同字幕组'文件才打包(典型触发 = 首次库存导入、批量下载完成),上限 20/次
- 批内模板化强(实测单模板 23 集):LLM 解出模板,其余槽位填充;数组输出 + 逐项校验,失败项单独重试不连坐
- 上下文注入:top-5 别名 + 集数约束(该 series 放送进度),压缩幻觉空间
- 省钱双引擎:**订阅场景靠记忆飞轮,库存导入靠合批** —— L2 两级 key 实测 458 key 覆盖 94.3%(见 5.1b)
- 小模型先上,校验不过才升级大模型;带错误反馈重试一次;结果先进待确认区按 5.1 规则沉淀

### 9.4 项目亮点(与其他方案的差异,写 README/简历)

1. **Local-first 识别管线**:anitopy 本地解析 + 置信度路由,LLM 仅兜底 —— 对比 AutoBangumi 3.3 的
   LLM-primary 方案,LLM 调用降低 X%,token 成本趋近零
2. **双循环记忆**:解析记忆(成功沉淀)+ 纠错学习(人工纠正=最高权重、bypass_list 负记忆防重复犯错),
   越用越准、越用越省,且记忆质量可监控
3. **洗版引擎**:透明可配的质量评分公式 + 升级阈值 + 洗版上限(对标 ani-rss 的洗版,但评分规则开放可解释)
4. **季度状态机 + 缺集回补**:COLLECTED 后自动降频,资源占用随番剧完结而衰减
5. **可观测性即功能**:@xyflow/react 管线可视化 + 各级命中率 + LLM 调用率周曲线 + 记忆质量报表
6. **确定性边界纪律**:AI 只碰非结构化转换,调度/评分/决策全部确定性代码,行为可复现可测试
